# Data_Analysis_Agent

用自然语言问业务数据。Agent 自己决定查哪张表、写什么 SQL，答案附带口径说明与数据限制，表格由界面渲染。

底层是 **大模型 Function Calling + SQLite 只读查询**，为学习 Agent 编排、工具契约与评测而做，不是生产系统。

## 功能

- **只读 SQL 工具**：白名单只放行 `SELECT` / `WITH`，连接用 `mode=ro` + `PRAGMA query_only`，5 秒超时中断
- **双通道结果**：同一份查询结果，Agent 只看前 25 行，界面显示全量；两者各自带总数与截断说明
- **口径查询**：20 条业务规则（订单范围、退货率算法、金额单位…）由 `policy_lookup` 按主题检索，不让模型自由发挥
- **表结构查询**：9 张表的语义说明（字段含义、枚举取值、外键、唯一约束）由 `inspect_schema` 提供
- **结构化错误**：工具统一返回五字段信封 `{ok, error_type, error_message, retryable, data}`，模型能区分"改参数重试"和"没救"

## 快速开始

要求 Python 3.14+（实测 3.14.5）。

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows；macOS/Linux 用 source .venv/bin/activate
pip install -r requirements.txt
```

在项目根目录建 `.env`，填三项：

```
API_KEY=你的API Key
BASE_URL=你的BASE_URL
MODEL_NAME=想调用的模型名
```

启动界面：

```bash
python agent_software/app.py
```

当前版本主要面向技术演示与结果复现，优先保证核心流程与工程实现的可读性，暂不包含云端部署、权限控制和多租户隔离。服务默认绑定127.0.0.1:7860，实际访问地址以终端显示为主。由于工具层数据库连接目前是进程级全局状态，示例配置将并发上限设为1。

## 用法示例

三个例子分别覆盖：一次提问产生多条查询、结果超过 Agent 的 25 行视野、与数据库无关的问题。

**① 一次提问产生多条查询（实测 8 条成功查询）**

> 九月都卖出去啥了？各卖了多少？

| 区域 | 实际显示 |
|---|---|
| 左侧表格 | 默认展示**最近一次**成功查询（如"九月各状态订单数"，5 行）；上方出现下拉框，列出本次全部 8 条查询，选中即切换。切到"商品销量 / 销售额 / 订单数"那条才是用户要的表 |
| 结果区提示 | 「当前查询共 5 行，已全部展示」；切到 45 行的状态核对查询时变为「当前查询共 45 行，Agent 仅分析前 25 行」 |
| 右侧回复 | 6 种商品的销量、销售额、订单数，附"仅统计已完成订单、不扣退货"的口径说明与数据限制 |
| 底部信息 | 干净库 · 8 步 · 45k tokens · 耗时（示例值，每次运行不同；切换结果时这几项不变） |

**② 结果超过 Agent 的视野**

> 八月所有商品的每日销量是多少

8 个商品 × 31 天展开，结果 248 行（含 0 销量的日期）：左侧表格展示全部 248 行（500 行上限内），右侧回复只分析前 25 行（8/1–8/4），并明确说明"详细清单共 248 行，你看到的是前 25 行，其余 223 行由界面展示"。（默认展示的是最后一条 8 行汇总，可在下拉框切到这条 248 行结果。）

**③ 与数据库无关的问题**

> 今天吃什么？

先查一次口径与表结构、确认库里没有餐饮类数据，然后明确说明"只连了电商订单库，不能凭猜测作答"，并列出可以查的方向。左侧没有表格，显示「本次没有可展示的成功查询结果」。

> 注：默认展示的是**最近一次**成功查询，不一定是你要的那张表——这是有意的取舍，原因见「已知限制」。

```
评测集/            22 道题的题面与判据
SQL_test/          造数脚本（运行时不被 Agent 导入）

```

## 关键设计

**1. 编排层不碰数据库。** `main.py` 只负责"问模型 → 执行工具 → 把结果塞回对话"，不知道什么是订单、什么是库存。业务全在工具里，所以口径改动不需要碰循环。

**2. 错误要分类，不只是"失败"。** 信封里的 `retryable` 表达的是"改一下输入再调有没有意义"：SQL 写错可重试，越权访问不可重试。这让模型不必靠猜。

**3. 只读是三道防线，不是一道。** 前端剥注释后白名单校验、连接以只读模式打开、`query_only` 兜底，再加 5 秒进度中断。单靠任何一道都够被绕过。

**4. 截断必须显式。** 模型静默拿到前 25 行却以为是全部，会给出"看起来对、统计偏错"的答案——这比报错更难发现。所以总行数由工具返回，截断说明由程序补，不依赖模型自觉。

## 评测

22 道题（常规 10 / 边界 7 / 脏库 5），temperature 固定 0.2，每题重复 3 次取中位。

- 综合分 **93.3**，常规 10/10、边界 7/7、脏库 4/5，平均 6.8 步
- 唯一未通过：脏库-03（开放题，三次里仅 1 次发现"商品已删除后仍下单"）
- 加入 `inspect_schema` 的 A/B 对照（同题同模型同温度，唯一变量是工具注册）：

| 指标 | 无该工具 | 有该工具 |
|---|---|---|
| 关键数字答对 | 60 | **62** |
| 平均步数 | 6.7 | **6.2** |
| 撞 12 步上限 | 4 次 | **1 次** |
| 直接查系统表拿结构（`sqlite_master`） | 86 次 | **0 次** |

## 已知限制

- **判分半自动**：`make_judgement.py` 对 3 条失败用例写死了人工裁定，`judge_helper.py` 里另有关键数字对照表。不等于客观评测，所以原始轨迹全部落盘可复核。
- **无多轮对话**：每次提问是独立的 `run_agent` 调用，暂不保留上下文。
- **无并发**：数据库连接与结果缓存是模块级全局变量，Gradio 并发锁为 1。
- **单机 SQLite**，未做迁移、未做权限体系。
- **界面展示上限 500 行**：当前数据量到不了，属遗留防御值。
- **25 行是单次上限**，没有"单轮累计"闸门；12 步理论上可累积 300 行。
- **默认展示"最近一次"成功查询，不保证是用户要的那张表**：程序不判断哪条是"主结果"——按行数最多来选会被审计类查询占用（实测：主查询 8 行销量，被一次 116 行的状态核对挤掉），所以改为多条结果由下拉框手动切换。
- **测试覆盖有限**：`tests/` 只有两个零依赖脚本，覆盖结果缓存与展示层；Agent 循环、工具参数校验、口径检索尚无自动化测试。
